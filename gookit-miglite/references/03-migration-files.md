# Migration files

## Naming

Generated by `miglite create NAME`: `YYYYMMDD-HHMMSS-NAME.sql`, local time (`20060102-150405` layout;
HHMMSS = hour, minute, second).

Accepted by the loader (regex `^(\d{8})-(\d{6})([\w-]+)\.sql$`):

- 8 digits + `-` + 6 digits, then the name. `YYYYMMDD` must be a valid date or the file is rejected;
  the 6 digits need only be digits (falls back to a date-only parse), e.g. `20260504-100070-x.sql` works.
- Name chars: letters, digits, `_`, `-` only. Dots/spaces/non-ASCII break matching.
- A leading `-`/`_` of the name part is trimmed (the separator is not strictly required by the regex).
- The full file name is the version stored in `z_schema_migrations.version` (max 160 chars). Renaming an
  applied file makes it look pending and breaks `down`.
- Sorting: by `YYYYMMDD-NNNNNN` prefix, ties by full file name. `down` orders records by version string desc.

Discovery (`migrations.path`):

- Recursive by default (`recursive: true`); `_`-prefixed files and directories are ignored.
- Comma-separated paths are merged and sorted together; `${ENV}` and `{driver}` expand.
- Only `*.sql` files are considered; every non-`_` `.sql` file must match the naming rule, otherwise `up`/`status`
  fail with `invalid filename format`.
- `{driver}` lets you keep per-DB dirs: `path: ./migrations/{driver}` (mysql/postgres/sqlite/mssql).

## Structure

```sql
-- Migrate:UP
CREATE TABLE post (id int NOT NULL, title text, PRIMARY KEY(id));
CREATE INDEX idx_post_title ON post(title);

-- Migrate:DOWN
DROP TABLE post;
```

Parsing rules (pkg/migration.ParseContents):

- Marker lines: trimmed line starts with `-- Migrate:UP` / `-- Migrate:DOWN` (case-sensitive; anything
  after the marker on the same line is ignored). Not `-- +migrate Up` or `-- migrate:up`.
- Text before the first marker is ignored.
- Within a section, blank lines are removed and lines beginning with `-- ` are dropped as comments.
  (`--comment` without the space, or trailing `-- x` after SQL, is kept and sent to the DB.)
- Empty file or empty UP section: error `does not contain valid SQL in '-- Migrate:UP' section`.
- DOWN is optional. If missing/empty, `miglite down` warns "Skipping empty DOWN migration" and leaves the
  record as applied.
- Each section is executed as a single `tx.Exec(section)`, not split. SQLite and Postgres drivers accept several
  statements in one Exec (lib/pq without args does); MySQL requires `multiStatements=true` (added
  automatically to the config DSN). Avoid `$$` bodies/triggers on drivers that cannot run them in one Exec.
- Transaction: each file in one tx together with the record insert. MySQL (and others) auto-commit DDL, so
  a failure mid-file may leave partial changes - keep MySQL migrations small.
- Migrate options (`-- Migrate-option:` / `UP(option=...)`) are TODO in the source, not supported.

## Status values

`up` applied, `down` rolled back (re-applied by the next `up`), `skip` skipped via `miglite skip`,
`pending` (no record). Output labels: applied / rolled / skipped / pending.

## Practice

- One logical change per file; never edit an applied file; write a DOWN whenever it is reversible.
- Use `miglite exec` for ad-hoc one-off SQL; it does not record anything.
- Use `miglite skip FILE` to baseline an existing database whose changes already exist.
